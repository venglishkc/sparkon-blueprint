The engagement

Northbridge is a $6.2B-asset regional commercial bank. Its core banking, loan origination, and deposits run on rock-solid systems of record — but the front office (relationship managers, lending, treasury) runs on spreadsheets and an aging CRM. Revenue teams can't see a whole relationship, the loan pipeline lives in a workbook, and cross-sell between lending and treasury happens by memory.

What's broken today

  • No single view of a relationship. Lending, treasury, and deposits each hold a fragment.
  • Pipeline in spreadsheets. No forecast leadership trusts; deals go stale unseen.
  • Cross-sell leakage. $15M loans funding with one treasury product attached.
  • Referrals evaporate between divisions with no hand-off trail.
  • Compliance can't audit who touched what, when.

What we're building

  • HubSpot as the engagement layer — not a core replacement. It sits beside Fiserv/nCino and adds the relationship intelligence they lack. Field-level ownership and conflict rules are set out in the System-of-Record table on the Integrations tab; the sync runs through iPaaS middleware with staging and an error queue, not a point-to-point connector.
  • A banking-native data model — native Company (relationship householding), Deal (lending pipeline) and Ticket (referrals), plus exactly two custom objects: Facility and Treasury Product.
  • Governed pipelines for Commercial Lending, Treasury, and cross-division Referrals.
  • An AI intelligence layer — a weekly RevOps brief + next-best-action for every RM. Execution mechanics (trigger, payload scope, auth, retention, failure mode) are specified in Engineering Notes, not left as a connector name.
  • Audit-ready governance — permissioning, property-level controls, and activity retention mapped to the bank's existing ISO 27001 / SOC 2 control set (HubSpot is in scope as a processor here, not a substitute for the bank's certification).
Design principle. In a bank, HubSpot is the customer-engagement and communication layer that sits alongside — not against — the core. Systems of record stay authoritative; HubSpot becomes the place revenue teams actually work. Every architecture decision below protects that boundary.

CRM architecture

A banking-native data model built on a deliberate rule: bend native objects first, add custom objects only where the cardinality demands it. Companies, Deals and Tickets carry most of the model — two custom objects earn their place — under a governed property hierarchy built for reporting, not just data entry.

Workflow automation

Every workflow is specced from the process first, approved, then logged — so the portal doesn't rot into hundreds of orphaned automations nobody understands. Six of the core builds:

Routing

Lead → RM assignment

Trigger: new Relationship created. Logic: route by naics_sector + territory + book capacity → set primary_rm, create intro task, start SLA timer. Guard: round-robin fallback if owner unset in 4h.

Hygiene

Stale-deal & going-cold alerts

Trigger: days_in_stage > 21 OR last_activity > 14d. Action: flag deal, notify RM, escalate to manager on day 30. Why: this is what keeps forecast honest.

Revenue

Treasury cross-sell trigger

Trigger: Loan Opportunity enters Credit Approval AND treasury_products_held < 2. Action: create treasury cross-sell task + draft the play — before the loan funds, while attention is high.

Compliance

KYC gate — a layered control, because HubSpot has no synchronous validation

State the platform limit plainly: HubSpot cannot synchronously validate a value on stage change. Required stage properties only enforce that a field is populated — "Pending" satisfies them — and workflows fire asynchronously after the change commits, so neither is a true block. So the gate is layered: (1) kyc_status is required on the Underwriting stage, so it can't be empty; (2) it is edit-restricted to compliance and the integration user, so an RM can't self-clear it; (3) an async workflow reverts any deal that reached Underwriting while not Cleared and logs a compliance task. And the honest architectural call: if the regulator needs a hard stop, it belongs in the LOS (nCino), not the CRM — HubSpot enforces process discipline here, not the control of record.

Retention

Maturity & annual-review engine

Trigger: Facility maturity_date or Relationship next_review_date within 90d. Action: renewal opportunity + RM task. Why: renewals are the cheapest revenue in the book.

Coordination

Referral hand-off

Trigger: Referral created. Action: notify receiving division, set owner, timestamp the hand-off, close the loop back to source RM. Value: no more lost cross-division referrals.

State management & edge cases — where enterprise workflows actually live

Trigger → action is the easy 20%. Each spec above also carries the unglamorous 80% that keeps a portal from corrupting itself:

  • Re-enrollment & un-enrollment rules — explicit per workflow, so a deal that bounces back a stage doesn't double-fire tasks or skip the KYC gate.
  • Loop / circuit breakers — property-write workflows guarded so A-updates-B-updates-A can't cascade; hard caps and "if unchanged, exit" branches.
  • Missing-required-property handling — a fallback branch that routes to a data-fix task instead of silently failing enrollment.
  • Race conditions — integration syncs vs. user edits ordered with last-write rules so a nightly core sync never clobbers a rep's in-flight note.
Build discipline. Each of these ships with a build-log entry (trigger, enrollment criteria, actions, owner, test result) so the next person — or an auditor — can read the portal like documentation. A prose promise doesn't hold; a logged, tested workflow does.

System-of-Record hierarchy & sync direction

Every field has exactly one authoritative source. Naming the SoR per object up front is what prevents the classic two-systems-fight-over-one-record failure.

Facility balances, risk rating, exposureFiserv / FIS (core)Core → HubSpot (read-only)Core always wins; field locked in HubSpot

Middleware, not point-to-point. Core/LOS syncs run through an iPaaS layer (Workato / Boomi / MuleSoft) with staging tables, a sync-error queue, field-level write permissions, and idempotent retries — not a naive bidirectional connector. That's the difference between a clean diagram and a banking integration that survives a batch window and PII-masking rules.

Data migration plan

  • Extract from legacy CRM + spreadsheets; profile for quality first.
  • Cleanse & dedup — householding logic to merge fragmented relationships.
  • Map to the new object model with a documented field-mapping sheet.
  • Stage & validate in a sandbox; reconcile record counts and spot-check.
  • Cutover in a controlled window with rollback; then verify associations.

Governance & security (ISO 27001-aligned)

  • Role-based permissions — RMs see their book via team partitioning on record access; leadership sees all; compliance read-all. Worth stating plainly: HubSpot's field-level visibility is coarser than a core banking system's, so partitioning does the heavy lifting.
  • Property-level edit restrictions — risk & exposure are read-only to RMs and written only by the integration user.
  • Naming conventions & property governance to keep reporting clean over time.
  • Activity logging & retention for audit; PII handling per policy.
  • Least-privilege API keys and monitored integration sync health.

Stage 4 of the loop. The agent reads the pipeline and writes a weekly brief: what's at risk, where the cross-sell is, and the next action for each RM. Core design rule: every number is computed deterministically in code and the narrative is generated from those computed facts — the model layer writes judgment, never arithmetic.

Phasing — crawl, walk, run

No bank executive signs off on a six-month big-bang CRM program without seeing value first — and they shouldn't. Each phase stands on its own and returns something usable before the next one starts, so the program can be paused after any phase and still be worth what was spent.

PHASE 1 · CRAWL — weeks 1–5

One team, one pipeline, clean data

Scope: native Company/Deal model, the Commercial Lending pipeline, hygiene workflows, Aircall logging, a leadership dashboard. No custom objects, no core integration.
Value delivered: a forecast leadership can trust, on real data, inside six weeks.

PHASE 2 · WALK — weeks 6–12

The banking data model

Scope: Facility & Treasury Product custom objects, nCino sync, migration of historical facilities, cross-sell and renewal automation, referral pipeline.
Value delivered: whole-relationship view and the treasury cross-sell engine — the revenue case.

PHASE 3 · RUN — month 4+

Core sync & the intelligence layer

Scope: Fiserv/FIS read-only sync via middleware, Snowflake warehouse, the RevOps Intelligence Agent and next-best-action, full governance hardening.
Value delivered: the self-learning loop — and it runs on data already proven clean.

Why this order. The riskiest, most expensive work (core-banking integration) is deliberately last, not first — so the client banks a trustworthy forecast in week 5 and funds Phase 3 on the strength of a working system rather than a promise. It also means a stalled core-IT dependency delays the AI layer, never the whole program.

Adoption & change management — because bankers resist CRMs

Kill manual logging

Aircall auto-logs calls; mobile app + Sales extension capture activity so RMs type as little as possible. Adoption dies on data-entry friction, not on features.

Champions, not mandates

Pilot with one lending team, turn their wins into the internal case, then roll out — beats a top-down "everyone's on HubSpot Monday."

Measure adoption, not just build

Track logged-activity rate and pipeline-hygiene score per RM. A system nobody uses is a failed project no matter how clean the build is.

Engineering notes — assumptions & trade-offs

The honest half of any real scope. These are the constraints, decisions, and risks I'd put in front of the client on day one — because the parts that get hard are exactly the parts worth naming early.

Platform prerequisites

The two custom objects (Facility, Treasury Product) assume a HubSpot Enterprise tier (Sales/Service Enterprise or Ops Hub) — custom objects, calculated properties, and field-level permissions aren't available below it. Keeping Relationship on native Company is partly a licensing decision too. Right-sizing the license is part of scoping, not an afterthought.

Custom objects vs. native — the trade-off I'd defend

Modelling everything as custom objects is the classic over-engineering trap: they sit outside default report builders, complicate line-of-sight attribution, and consume API. So the rule I applied to the architecture is bend native first — Relationship is a Company with parent/child householding, Loan Opportunity is a Deal on a custom pipeline, Referral is a Ticket. Only Facility and Treasury Product earn custom objects, because a single relationship holds many of each with their own lifecycles — a 1:N shape that genuinely breaks the native model. That's two custom objects instead of five, and the Custom-Report-Builder complexity we do accept buys something specific.

SystemConnectorReal lift

Where I'd focus risk. The core and LOS integrations are the long pole, not the HubSpot build. I'd de-risk them in a spike during Sprint 0 rather than discover the effort in Sprint 3.

Rollups: use native first, code only at the edges

credit_exposure (SUM) and treasury_products_held (COUNT) are built as native Enterprise rollup calculation properties over the Facility / Treasury Product associations — no custom code, no API budget, no maintenance debt. Reaching for Ops Hub custom code when a native rollup exists is a classic over-engineering tell. Custom code earns its place only at the edges native rollups don't reach — conditional aggregations (e.g. exposure excluding matured facilities), cross-object math, or currency normalisation — and there I'd add a nightly reconciliation job so a missed event never leaves exposure silently stale. Worth scoping either way: rollups over custom objects assume Enterprise.

Honest timeline

The ~10-week plan is a Phase-1 MVP: CRM model, pipelines, workflows, dashboards, and the AI layer on clean migrated data. Full bidirectional core/nCino integration and a complete historical migration realistically extend the program to ~4–6 months, phased. I'd rather commit to a real date than a hopeful one.

AI data governance — the one a bank's CISO will ask about

Sending customer financial data to a public LLM endpoint is a non-starter in banking. How I'd actually deploy the AI layer:

  • Enterprise, no-retention inference — Azure OpenAI or AWS Bedrock in the bank's own tenant, with a signed DPA and zero-retention terms. Not the public API.
  • Deterministic layer keeps math & logic local — the model never computes; it only writes narrative over pre-computed facts (see the AI tab).
  • Entity anonymization option — tokenize relationship names / amounts before inference and re-hydrate on return when policy requires it.
  • Human-in-the-loop — the agent drafts the brief; an RM or manager approves. No autonomous action on customer accounts.

This is the difference between a demo and something a regulated institution will actually run.

How the AI layer actually executes — not a "connector"

Saying "Claude/OpenAI/Breeze connectors" is a slide, not an architecture. Breeze covers embedded copilot and enrichment use cases; it is not a general LLM pipeline runner, so the weekly brief runs outside it:

  • Trigger & compute: a scheduled job (Ops Hub custom-code action or an external worker) pulls the open pipeline via the CRM Search API with pagination, and computes every figure in code.
  • Payload discipline: only the aggregated fact sheet goes to the model — tens of rows, not the CRM. That keeps the prompt inside context limits and shrinks the data-exposure surface to a known, reviewable payload.
  • Auth & secrets: private-app token scoped read-only to the objects it needs; model API key held in a secrets manager, never in a workflow action or client-side code.
  • Storage scope: the returned narrative is written back as a Note on the owner record and to the warehouse; no customer data is retained by the inference provider (zero-retention tier).
  • Failure mode: if the model call fails, the deterministic fact sheet still publishes — the numbers never depend on the LLM being up.
